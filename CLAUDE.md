# Loadless Delivery Platform

Multi-vendor delivery management platform (Lebanon). Three roles: ADMIN / VENDOR / DRIVER.
Full architecture plan: `~/.claude/plans/delivery-platform-squishy-wall.md`.

## Stack & layout

- pnpm workspaces monorepo: `apps/web` (Next.js 15 App Router), `apps/api` (NestJS 11 + Prisma 6 + Socket.IO), `packages/shared` (pure TS contracts).
- Postgres 16 + Redis 7 via `docker-compose.dev.yml` (apps run natively: `pnpm dev`).
- Dev ports: web **3100**, api **4100** (4000/3000-3003 belong to other projects on this machine).
- `packages/shared` is the single source of truth for enums, zod DTO schemas, socket event contracts, phone normalization, money helpers. It must stay pure (no Nest/Prisma/React imports — ESLint-enforced). It compiles to CJS (`pnpm --filter @loadless/shared build`); rebuild after editing it (or run its `dev` watcher).

## Non-negotiable invariants

- **Money**: BigInt integer minor units + currency (LBP exponent 0, USD exponent 2). Commission in basis points. `calcCommission` in shared is the ONLY commission math. Earnings = charge − commission (never computed independently). BigInt serializes as strings on the wire (global interceptor).
- **Financial snapshot** (commissionBps + amounts) is computed atomically at driver ACCEPTANCE (per-driver rate: `commissionOverrideBps ?? platform default`), cleared on release, recomputed on admin reassign. Never at order creation.
- **Concurrency**: all order transitions are conditional atomic `updateMany` with the full guard in the WHERE clause (status + driverId + ownership), inside a transaction that also writes `order_status_history`. `count === 0` ⇒ 409 with a stable code. Never fetch-then-update. Socket events emit only AFTER commit.
- **State machine**: transition table lives in `packages/shared/src/order-transitions.ts`. Vendor cancels ONLY while PENDING. Driver release only before pickup. DB CHECK constraints back all of this (see `constraints_and_guards` migration).
- **Phones**: normalize via shared `normalizeLebanesePhone` everywhere; stored as `+961…`; DB CHECK regex backstops it.
- **Locations are Google Maps LINKS, not map pins** (product decision): the customer shares a maps link on WhatsApp, the vendor pastes it (`Order.deliveryMapsUrl`, `CustomerAddress.mapsUrl`), the driver taps Navigate to open it. There is NO map-picker UI and no Leaflet dependency; lat/lng columns exist but are unused v1.
- **Admin manages everything**: customers (name + identity phone — phone change is admin-only — plus address book) via `/admin/customers/:id`; drivers/vendors CRUD; orders assign/reassign/cancel.
- **Customer 360**: the phone lookup returns the WHOLE profile (identity + addresses + stats + recent orders) in ONE round trip — the vendor is on a live call, so no second fetch and no mid-call spinner. Every order-derived number is scoped through `customerOrderScope()` in `apps/api/src/customers/customer-order.scope.ts` — the ONLY place an order `where` is built for customer routes. A vendor sees their own trade and **nothing else** — there is NO cross-vendor figure in the payload, not even a bare count of orders elsewhere (that still tells one shop another shop serves this customer). Adding a customer-scoped order read without that helper is a review-blocking mistake.
- **The vendor↔customer relationship** (`customer_vendors`): customers stay GLOBAL, but a vendor's *relationship* with one is private. A link row appears when a vendor creates a customer or orders for them, and is maintained by **Postgres triggers**, not app code — an order implies a relationship, so it must be written in the order's own transaction whatever inserted the order (service, script, or test fixture). Counters never decrement (a cancelled order still happened). What each party may change:
  - **Vendors ADD, only ADMIN edits** (product decision — the tech lead's ruling). phone (identity) → ADMIN; **the global name** → ADMIN, no vendor, not even the one who added the customer; **any saved address** → ADMIN edits and archives, while ANY vendor may add one. The three admin-only routes are narrowed with a method-level `@Roles('ADMIN')` inside the ADMIN+VENDOR controller — `RolesGuard` uses `getAllAndOverride([handler, class])`, so the handler wins and the paths never move. **This is affordable only because the per-order address is unrestricted** (`orders.delivery_*`): a vendor never has to edit the profile to get a delivery to the right door, so removing the pen costs them nothing operationally.
  - **Your alias** (`customer_vendors.display_name`) → you only, and nobody else — vendor, driver or otherwise — ever sees it. It is now the ONLY customer field a vendor can write, and `nameScope` is therefore `MINE` for every vendor and `GLOBAL` only for admin. An alias equal to the base name is stored NULL so you keep following admin's later corrections.
  - **One row per place** (product decision, confirmed): the address book is a SHARED list, not per-vendor copies — the dedupe index is not vendor-scoped. An identical add is a no-op returning the existing row, so `addAddress` reports `created` AND `matchedOn` (`link` | `text`); the UI must never say "saved" when created is false, nor blame the address when it was the pin that collided. The maps-link enrichment (filling a NULL `mapsUrl` on an existing row) is **admin-only** for the same reason every other address edit is; a vendor's link rides on the order, which is what the driver taps.
  - Vendor payloads still carry a computed `ownership: MINE|OTHER|PLATFORM` and `addedByYou: boolean` (informational — admin uses `ownerVendorName`, vendors get the "Added by you" badge) — **never** a foreign `vendorId` or business name (that would reconstruct a competitor's client list). Everything goes through `projectCustomer`/`projectAddress` in `customer.select.ts`.
- **Every order starts blank** (product decision): there is NO repeat-order flow — no "last order" banner, no Repeat buttons, no stashed draft. Nothing from a previous delivery (charge, notes, instructions) may ride along into a new one. The only things a `/vendor/orders/new` link may carry are `?phone=` and `?addressId=`, both read once on mount and then cleared from the URL. Re-adding a prefill is a product regression, not an improvement.
- **Search is incremental, but enumeration is not**: `/vendor/customers` has ONE box. A name or any prefix of a number filters the vendor's OWN customers live; a *complete* phone number opens anyone on the platform. **A name never reaches past your own customers** — a name-searchable directory IS a competitor's client list. The single exception is `GET /customers/lookup` (`platformLookup`), which answers "who else has a number starting with these digits": phone digits only, at least `PLATFORM_LOOKUP_MIN_DIGITS` (6) of them, capped at 10 with a `hasMore` flag, **identity only** (name + phone — exactly what typing the full number already gives), the caller's own customers excluded, and throttled to 20/min. Every one of those limits is load-bearing; widening any of them turns it into the directory the product withholds. Phone prefixes must go through shared `phoneSearchDigits` (numbers are stored `+9613123456` with the leading 0 dropped, so matching the literal typed "03 12" silently finds nothing).
- **Vendors get no bulk directory**: `GET /vendor/customers` lists only their own links; `WHERE cv."vendor_id" = <JWT>` is the single most security-critical line in the feature. Anyone else is reachable by typing a full phone number and no other way. Scope helpers (`vendorCustomerScope`, `adminVendorLinkFilter`, `resolveCustomerName`, `addressOwnership`) live beside `customerOrderScope` so there is one file to audit.
- **Addresses are deduped on write**: `CustomersService.saveAddressInTx` is the one path (explicit route + order creation). Matches on maps link, else `normalizeAddressKey` (whitespace+case). A partial unique expression index is the race backstop — recover via ON CONFLICT DO NOTHING, never by catching P2002 inside an interactive transaction (the tx is already aborted). The SQL expression and `normalizeAddressKey` must stay in step.
- **Login identity is split by role** (product decision): DRIVERS sign in with phone + password; ADMINS and VENDORS sign in with email + password. `users.email` / `users.normalized_phone` are nullable uniques with a role-identity DB CHECK. One login form accepts both (anything with "@" = email).
- **Sessions are permanent** (product decision): one login per device, never auto-expired — 400-day sliding refresh window, re-extended on every use. Sessions end only on explicit sign-out, admin suspension/password change, or refresh-token theft detection. Never add idle timeouts or forced re-login.
- **Authorization**: ownership via query scoping (`vendorId: user.vendorId` in the WHERE), never fetch-then-compare; foreign resources are 404. No scattered `role === 'ADMIN'` — use PolicyService.
- **Prisma custom SQL** (CHECKs, partial indexes, triggers, sequences) goes in hand-edited migrations via `prisma migrate dev --create-only`.

## API conventions

- Base path `/api/v1`. Success `{ data, meta? }`; errors `{ error: { code, message, details?, requestId } }` with codes from shared `ERROR_CODES`. Validation via `ZodValidationPipe` + shared schemas (NOT class-validator).
- Domain errors are `AppException` only.
- **The web app talks to the API through `apps/web/src/lib/api-client.ts` and nothing else.** It is where the ONE silent refresh-and-retry on 401 lives, so a raw `fetch` silently opts out of it: the 15-min access token expires, the long-lived cookie still satisfies the middleware, and the page renders a shell whose every list 401s forever — an empty table, not an error. Use `api.get` for a bare payload, `api.page` when the `{ data, meta }` envelope is needed (pagination), `api.postForm` for uploads.
- **Uploads live on the VPS disk** (product decision): `STORAGE_DRIVER=local` — its default. An R2 adapter exists (`files/r2.storage.ts`) and stays unused until volume actually demands it. **Consequence for deployment: the uploads directory MUST be a persisted Docker volume.** The Dockerfile creates `/app/uploads` inside the image, which is wiped on every container replacement — a bind mount or named volume is the only thing standing between a redeploy and every driver photo and vendor logo disappearing.
- **Driver photos** are not public files. `files.service.download` authorises them against the DRIVER ROW, never `ownerUserId` (the uploader is the admin filling in the form). The FACE photo reaches a vendor the driver has actually carried an order for — that is the handover check it exists for; the BIKE photo is admin-only. A refusal is 404, not 403: confirming the file exists would itself say who drives for whom.
- Redis caching allowlist ONLY: analytics aggregates (short TTL), platform settings (invalidate on update), throttler/deactivation state. Order data is NEVER cached.

## Workflow

- `docker compose -f docker-compose.dev.yml up -d` then `pnpm dev`. Dev accounts: admin `admin@gmail.com`, vendor `vendor@gmail.com`, driver `70 123 456` — all password `loadless`.
- Verify with `pnpm -r lint && pnpm -r typecheck && pnpm -r test` before finishing any task. Integration: `pnpm --filter @loadless/api test:integration`. Browser e2e: `bash apps/web/e2e/prepare.sh && (cd apps/web && pnpm e2e)` — 45 tests covering every flow; specs live in `apps/web/e2e/`.
- The reusable design system lives in the tokens in `apps/web/src/app/globals.css` (shadows, status colors, `surface-brand`); UI primitives in `src/components/ui/` are restyled on those tokens — never introduce raw hex in components.
- **Performance is measured, not assumed**: `bash apps/api/test/perf/run.sh` runs the real API against 400k orders / 120k customers and prints p50/p95/p99 per endpoint (`CONC=1` for single-user latency). Baselines and the two traps it caught are in `apps/api/test/perf/README.md`. Two rules that came out of it:
  - **Never put a relation `_count: { select: … }` on a paginated list** — Prisma compiles it to a full-table GROUP BY per relation, joined and only then limited (measured 1008ms → 47ms once counted against the page's own ids).
  - **`$transaction([a, b])` runs a and b in series on one connection.** Use it when the results are compared to each other on screen (the customer profile); use `Promise.all` when they are not (a page and its total).
- An index only supplies `ORDER BY` if the ordering columns follow the equality columns with nothing between. `orders(vendor_id, status, created_at)` could not order the vendor's DEFAULT unfiltered list, so it read every one of their orders — hence `orders(vendor_id, created_at DESC, id DESC)` and `orders(created_at DESC, id DESC)`.
- Migrations: run from `apps/api` with `DATABASE_URL` from `.env`.
- Deployment follows `~/playbooks/DEPLOY-PLAYBOOK.md` (Hostinger VPS, Caddy path-routing one hostname, only Caddy publishes ports).
